# Из GitHub Actions

**Официальный Action [`LayeroInfra/deploy-action`](https://github.com/LayeroInfra/deploy-action) публикует проект из пайплайна GitHub.** Он вызывает тот же `layero deploy`, только с токеном для CI.

```yaml
name: Deploy
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: LayeroInfra/deploy-action@v1
        with:
          token: ${{ secrets.LAYERO_TOKEN }}
          prod: true
```

## Сначала — нужен ли вам Action вообще

Если репозиторий [подключён к проекту](./github.md), сборка и так запускается при каждом пуше, и Action не нужен: вы добавите вторую копию той же работы.

Action нужен, когда **сборку надо выполнить в вашем пайплайне**:

- сборке требуются секреты, которых у платформы нет;
- используются приватные npm-пакеты из вашего реестра;
- перед публикацией должны пройти тесты, линтеры или кодогенерация;
- собираете монорепу и публикуете только один пакет из неё.

Тогда соберите проект в пайплайне и отправьте **готовую сборку**:

```yaml
      - run: npm ci && npm run build
        env:
          API_KEY: ${{ secrets.API_KEY }}
      - uses: LayeroInfra/deploy-action@v1
        with:
          token: ${{ secrets.LAYERO_TOKEN }}
          prebuilt: dist
          prod: true
```

## Токен

Вход через `layero login` действует неделю, поэтому для CI не годится: через семь дней сборки начнут падать с ошибкой 401. Для пайплайнов есть отдельный **бессрочный токен**.

1. Откройте страницу «Токены CLI и CI» — [app.layero.ru/settings/cli](https://app.layero.ru/settings/cli). Или выпустите токен из терминала: `npx layero@latest token create ci`.
2. Введите название (например, `GitHub Actions`) и нажмите «Создать токен».
3. **Скопируйте значение сразу** — оно показывается один раз, восстановить его нельзя.
4. В репозитории: Settings → Secrets and variables → Actions → New repository
   secret, имя `LAYERO_TOKEN`.

Отозвать токен можно там же, где его создавали. Сборки с этим токеном сразу начнут падать с ошибкой 401.

:::warning[Токен деплоит всё, но необратимое ему закрыто]
Токен работает с любым вашим проектом — своего разделения по проектам у него
нет. Заводите отдельный токен на каждый репозиторий: тогда утёкший токен вы отзовёте, не ломая остальные репозитории.

По умолчанию у токена права на чтение и деплой. Необратимое ему закрыто: удаление проекта и аккаунта, переименование организации, приглашение и удаление участников, отвязка карты и смена тарифа. Утёкший токен выкатит чужой код, но не сотрёт проект и не тронет деньги.

Команды баз данных (`layero db create`, `connect`, `disconnect`, `sql`, `delete`) и `layero deploy --db` тоже требуют прав `admin`. Если они нужны в CI, выпустите токен с ними: `npx layero@latest token create ci --scope read,deploy,admin`.

Права ограничивают именно токен для CI (он начинается с `layero_ci_`). Вход через `layero login` — обычный вход в аккаунт, он может всё то же, что и браузер.
:::

Если задана переменная `LAYERO_TOKEN`, CLI берёт токен из неё, а не вход из `~/.layero/config.json`. Поэтому на машине разработчика публикация уйдёт в аккаунт токена, а не в тот, под которым вы вошли.

## Параметры

| Параметр | Обязателен | По умолчанию | Что делает |
|---|---|---|---|
| `token` | да | — | CI-токен Layero |
| `project` | нет | из `.layero/project.json` | Проект-получатель (id или slug) |
| `name` | нет | — | Имя проекта при создании на первом деплое |
| `prod` | нет | `false` | Публиковать на основной адрес. Нужен только проекту с подключённым репозиторием: у проекта без репозитория каждый запуск и так публикует сайт по основному адресу |
| `branch` | нет | — | Не используйте: если параметр задан, Action останавливает шаг до загрузки, ничего не публикует и объясняет причину (код выхода 4). Превью веток делает подключённый репозиторий, а не Action |
| `prebuilt` | нет | — | Каталог с готовой сборкой |
| `type` | нет | автоопределение | Фреймворк: `vite`, `next`, `astro`, `static`… |
| `root` | нет | — | Монорепа: подкаталог как корень приложения |
| `working-directory` | нет | `.` | Откуда запускать деплой |
| `version` | нет | `latest` | Версия npm-пакета `layero` |

:::danger[`name` создаёт новый проект на каждом прогоне]
Если workflow должен раз за разом обновлять один и тот же проект, указывайте
**`project`** — он принимает id или slug и бьёт в конкретный существующий
проект.

`name` задаёт имя только **в момент создания проекта на первом деплое**. А
первым деплой оказывается каждый раз, когда в репозитории нет `.layero/project.json` — обычно его там и нет. При совпадении имён к адресу добавляется суффикс, поэтому сборка зелёная, просто адрес каждый раз новый.
:::

## Выходы шага

```yaml
      - uses: LayeroInfra/deploy-action@v1
        id: deploy
        with:
          token: ${{ secrets.LAYERO_TOKEN }}
      - run: 'echo "Опубликовано — ${{ steps.deploy.outputs.url }}"'
```

| Выход | Что содержит |
|---|---|
| `url` | Адрес, по которому опубликован деплой |
| `deploy-id` | Идентификатор деплоя |

Адрес дополнительно попадает в summary задачи — его видно на странице запуска,
без чтения логов.

## Превью на пулл-реквесты

Action превью не создаёт: всё, что он загружает, попадает в одно окружение
проекта. Чтобы у каждой ветки и пулл-реквеста был свой адрес,
[подключите репозиторий](../deploys/git-providers.md) — тогда превью
соберутся сами при каждом push.

:::warning[Проект без репозитория]
У проекта без подключённого репозитория любой запуск Action публикует сайт
по основному адресу — даже без `prod`. Не запускайте такой workflow для
пулл-реквестов: каждый PR заменит рабочий сайт.
:::

## Несколько примеров одним workflow

Матрица публикует несколько приложений из одного репозитория. Так устроен
[репозиторий примеров](https://github.com/LayeroInfra/examples) — четыре живых
сайта собираются и выкатываются при каждом push.

```yaml
    strategy:
      fail-fast: false
      matrix:
        include:
          - dir: vite-react
            output: dist
          - dir: astro
            output: dist
```

:::tip[fail-fast: false — не перестраховка]
Без него один сломанный пример отменяет выкатку всех остальных, включая уже
собранные. Одна битая зависимость гасит все живые демо.
:::

## Типовые ошибки

### `prebuilt_no_index`

```
'.next' has no index.html — nothing to serve
```

`prebuilt` предназначен для **статики** — каталога, в котором лежит готовый
`index.html`. Сборка Next.js в режиме сервера таким каталогом не является.

Для приложений с сервером `prebuilt` не указывайте вовсе: отправляйте исходники, и Layero запустит [приложение с сервером](../runtime/overview.md). Статический экспорт Next.js (`output: 'export'`), наоборот, отправляйте через `prebuilt: out`.

### `auth_required` сразу после старта

Токена нет или он пустой. Проверьте, что секрет называется именно `LAYERO_TOKEN` и передан в шаг. В CI команда не ждёт входа через браузер, а сразу останавливается с этой ошибкой.

### `address_required`

Имя проекта похоже на чужой бренд или на служебный адрес платформы. Возьмите
другое имя — например, с префиксом своей организации.

### `project_not_found`

`project` указывает на несуществующий проект. Проверьте id или слаг в списке `npx layero@latest projects list`. Не убирайте параметр: без него каждый прогон будет создавать новый проект — см. предупреждение про `name` выше.

## Другие CI-системы

Action — обёртка над обычным вызовом CLI, поэтому в любой другой системе
достаточно переменной окружения:

```bash
LAYERO_TOKEN=... npx layero@latest deploy --prod --yes
```

В CI CLI и так ничего не спрашивает, а `--yes` нужен, чтобы команда работала одинаково и в CI, и в терминале.
