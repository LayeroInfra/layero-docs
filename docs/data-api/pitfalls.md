# Грабли переезда

:::info[Бета-версия]

Data API работает в бета-версии и доступен на тарифе Pro. Чего ждать
от страниц, написано в [«Что такое Data API»](./index.md).

:::

Собрали по разборам инцидентов. Каждый пункт стоил кому-то от десяти минут до
получаса, и ни один не виден из кода.

## 1. Роль в миграции — по имени Supabase, не по шаблону

Пишите `TO anon`, `TO authenticated`, `TO service_role` — эти роли есть
в каждой базе. Искать «свою» роль шаблоном нельзя:

```sql
-- 🚨 ТАК НЕЛЬЗЯ
SELECT rolname FROM pg_roles WHERE rolname ~ '^u_.*_anon$' LIMIT 1;
```

Список ролей общий на весь сервер баз. Шаблон совпадёт с ролями чужих
арендаторов, и `GRANT` уедет **в чужую базу**: однажды так права на таблицы одного
продукта достались роли чужой организации.

```sql
-- Так правильно
GRANT SELECT ON public.entries TO anon;
```

Закрывают так же, как в Supabase: `REVOKE SELECT ON public.entries FROM anon;`
— публичный ключ теряет доступ сразу. Выдавайте права только этим ролям, не роли
своей базы из `layero.role(...)`: выданное ей поимённо `REVOKE … FROM anon` не снимет.

## 2. `INSERT … RETURNING` проходит политику **чтения**

`supabase-js` по умолчанию делает `.insert().select()`, то есть просит вернуть
вставленную строку. Возврат — это чтение, и он идёт через политику `SELECT`.

Классический случай: участника рабочего пространства добавляет триггер
`AFTER INSERT`, но право прочитать возвращаемую строку RLS проверяет до того,
как триггер отработает. Итог — `new row violates row-level security policy`,
хотя та же вставка без возврата проходит. Ошибка звучит как проблема со
вставкой, а причина в чтении.

Лечится политикой чтения, которая пускает и автора:

```sql
CREATE POLICY workspaces_read ON public.workspaces
    FOR SELECT TO PUBLIC
    USING (owner_id = auth.uid() OR EXISTS (
        SELECT 1 FROM public.members m
         WHERE m.workspace_id = id AND m.user_id = auth.uid()));
```

Либо вставкой без возврата: `db.from("workspaces").insert(row)` без `.select()`.

## 3. Функции ищутся в `api` и `public`, умолчания у них разные

Таблицы шлюз ищет в `api`, `public` и `app`, функции — в `api` и `public`.
Новая функция `public` вызывается по API сразу, как у Supabase; новая функция
`api` закрыта, пока не выдан `GRANT EXECUTE`. Вспомогательную функцию, которую
не должен звать интернет, кладите в свою закрытую схему (`private`,
`app_private`). `Accept-Profile` на поиск функций не влияет. Подробности —
[Функции и RPC](./rpc.md).

## 4. Имя аргумента функции — публичный контракт

Ключи JSON раскладываются по одноимённым аргументам, поэтому имя аргумента
видно снаружи и попадает в код каждого клиента. Внутри функции оно же
конфликтует с одноимённой колонкой (`column reference "token" is ambiguous`),
и локальная переменная не спасает — она подставляется и в `ON CONFLICT`.
Рецепт — там же, в [Функции и RPC](./rpc.md).

## 5. Пустой ответ — это работающая политика

`[]` в ответе значит «грант есть, строк по вашей политике нет». Это не ошибка
и не поломка доступа. Отличать полезно так:

| Ответ | Причина |
|---|---|
| `unknown_table` | таблицы нет в каталоге вашей роли — почти всегда грант ушёл не той роли |
| `no_table_grant` | таблица есть, права нет; готовый `GRANT` лежит в `hint` |
| `[]` | права есть, политика не пускает строки |

Проверьте в панели, что политика держит чужого: запрос выполнится **от роли
ключа**, а транзакция откатится.

## 6. Внутри шлюза `current_user` — не `authenticated`

Запрос вошедшего пользователя выполняется под служебной ролью вашей базы,
которая входит в группу `authenticated` (гостя — в `anon`, секретного
ключа — в `service_role`). Политики `TO authenticated` и права `GRANT …
TO authenticated` работают как у Supabase, а сравнение имени — нет:
`current_user = 'authenticated'` ложно, и проверка в триггере молча
пропускает всех.

Кто зовёт, проверяйте по токену:

```sql
IF auth.role() = 'authenticated' THEN …          -- вошедший
IF auth.uid() IS NULL THEN …                      -- гость
IF pg_has_role('authenticated', 'MEMBER') THEN …  -- членство в группе
```
