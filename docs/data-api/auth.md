# Вход пользователей

:::info[Бета-версия]

Data API работает в бета-версии и открыт пока не всем. Как получить доступ
и чего ждать от страниц, написано в [«Что такое Data API»](./index.md).

:::

Вход пользователей совместим с GoTrue, поэтому работает `supabase-js`:

```js
await db.auth.signUp({ email, password });
await db.auth.signInWithPassword({ email, password });
const { data: { user } } = await db.auth.getUser();
```

Поверхность: `/auth/v1/{token,signup,recover,verify,resend,authorize,callback}`,
`GET /auth/v1/user`, `PUT /auth/v1/user`, `POST /auth/v1/logout`. Есть вход по
ссылке из письма (magic link), PKCE и внешние провайдеры — включаются в панели
у базы.

## Роли — как в Supabase

В каждой базе есть роли `anon`, `authenticated` и `service_role`, поэтому
политики и гранты из миграций Supabase работают как есть:

```sql
CREATE POLICY entries_own ON public.entries
    FOR SELECT TO authenticated
    USING (owner_id = auth.uid());
GRANT SELECT ON public.entries TO authenticated;
```

Вошедший пользователь работает под ролью `authenticated`, гость — под `anon`,
секретный ключ — под `service_role`. В политиках доступны `auth.uid()`,
`auth.role()` и `auth.jwt()` — те же имена, что у Supabase.

Доступ устроен так же, как в Supabase:

- **Новая таблица в `public` открыта ролям сама** — права по умолчанию,
  как у них. Миграция без строк `GRANT` работает как есть, строки решает RLS.
  Таблица без RLS отдаёт все строки любому с публичным ключом — включайте
  RLS сразу, платформа предупредит о такой таблице.
- **Гость и вошедший — разные роли.** Политика `TO anon` действует только
  на гостей, `TO authenticated` — только на вошедших.
- **Секретный ключ (`service_role`) обходит RLS** — видит и меняет все
  строки, поэтому живёт только на вашем сервере.

## Подтверждение почты

Как у Supabase, новая Авторизация включается с подтверждением почты:
`signUp` не возвращает сессию, пока человек не перейдёт по ссылке из письма.
Без подтверждения кто угодно заведёт аккаунт на чужой адрес. Выключить
его можно в разделе «Авторизация» → «Подтверждать почту». У баз, где вход
включили до 26.10.2026, настройка осталась прежней — проверьте её там же.

### Тестовые пользователи — через admin API

Чтобы проверить вход без почтового ящика, заведите пользователя секретным
ключом, как в Supabase. Пользователь создаётся уже подтверждённым и входит
сразу:

```js
const admin = createClient(url, secretKey); // секретный ключ базы
await admin.auth.admin.createUser({
  email: "test@example.com",
  password: "надёжный-пароль",
  email_confirm: true,
});
// сменить пароль: admin.auth.admin.updateUserById(id, { password: "…" })
```

Запускайте это на сервере или скриптом, не в браузере: секретный ключ
обходит RLS.


## Вход из панели Layero: без второго пароля

Если приложение делаете вы сами, а его пользователи — ваша команда в Layero,
отдельный пароль заводить не нужно. Панель умеет обменять свою сессию
на сессию базы:

```
POST /organizations/<организация>/databases/<id>/api/app-session
```

Ответ — пара токенов, подписанных секретом **этой** базы, и адрес шлюза:

```json
{
  "url": "https://data.layero.ru/moya-baza",
  "access_token": "eyJ…",
  "refresh_token": "…",
  "expires_in": 3600,
  "user": { "id": "…", "email": "…" }
}
```

Токен кладётся в `authorization: Bearer …` рядом с публичным ключом — дальше
всё как у обычного входа: роль вошедшего, `auth.uid()`, политики.

Прав это не расширяет: доступ по-прежнему решают гранты и RLS, а владелец
организации не получает «видно всё». Пользователь в `auth.users` заводится или
находится тем же путём, что и при входе через внешнего провайдера. Повторный
обмен находит того же человека, а не создаёт второго.

## Секрет подписи — на базу

Токены каждой базы подписаны своим секретом. Подпись проверяет та база, к
которой обращаются, поэтому подменить имя базы в адресе недостаточно: токен
одного приложения у другого не пройдёт.
